# Travel Copilot 故障排查手册

故障排查应先确认页面类型、景区 POI、当前加载状态和系统配置，再给出原因与下一步。不能仅根据用户描述断言服务故障。

排查的目标不是一次列出所有可能性，而是根据用户提供的新证据逐步缩小范围。回答时应区分“已经观察到的现象”“可能原因”和“建议验证的动作”，并优先给用户一个可执行步骤。

## 中国地图黑屏

地图依赖高德 JS Key 与安全密钥。出现黑屏时先确认前端配置接口是否成功返回高德配置，再正常刷新页面。

如果配置缺失，页面会显示配置提示而不是地图。如果配置存在但仍黑屏，可能是 JS API 加载失败、浏览器网络异常、安全密钥不匹配或缓存仍指向旧前端资源。

配置接口成功只能说明页面拿到了参数，不能证明高德脚本已经成功加载。若地图容器存在但空白，可继续查看浏览器网络请求和 JS 控制台；若根本没有地图区域且出现配置提示，优先判断配置未就绪。客服不应让用户反复输入 API Key，也不应展示密钥内容。

## 省份地图没有光点

进入省份后，热门景区请求需要一定时间。光点可能在省份区域加载后稍晚出现，这不等同于地图失效。

若长时间没有光点，应检查省份 adcode、热门景区接口、后端日志和高德 Web 服务配置。不要建议用户重复点击省份造成重复请求。

“短时间没有”和“一直为空”是不同状态：前者更可能是异步请求尚未完成，后者才需要检查接口返回、adcode 是否正确、候选池是否为空和缓存是否异常。光点缺失也不一定是地图图层问题，景区候选列表为空同样会导致没有光点。

## 景区资料加载慢

景区页会先返回高德基础资料，再补充官网核验、天气、图片和 DeepSeek 摘要。首次生成通常比缓存命中慢。

后台准备任务会在用户悬停景区光点或进入页面时启动。离开页面不一定会取消任务，再次进入时可能回放已有事件并继续等待结果。

首次慢和重复刷新慢的原因不同：首次需要等待外部请求和生成任务，重复访问通常应命中已有缓存；如果重复访问仍持续很慢，再检查缓存是否失效、任务是否重复创建或后端是否异常。页面逐步出现字段是设计中的渐进加载，不应把“部分字段暂时为空”直接描述为整页失败。

## 图片完全没有显示

检查图片地址是否可访问、本地媒体缓存是否存在、景区后台任务是否完成，以及画廊是否返回了有效候选。

若画廊为空，可以重新加载；若数据库或媒体目录不可用，需要检查后端服务与 `data/media`。不要展示环境变量值或完整异常堆栈。

没有图片时先区分“候选列表为空”“候选有记录但 URL 无法访问”“缓存文件缺失”和“前端没有渲染”。只有查清所处环节，才能判断是数据采集、缓存、存储还是展示问题。用户侧可以先刷新；若基础资料正常而图片持续为空，再考虑后台任务和媒体服务。

## 图片模糊

图片模糊可能来自原始素材分辨率低、服务端压缩、浏览器展示尺寸过大，或候选图片本身不是高质量实景图。

原图分辨率不足时，图片的像素数量本来就少于展示区域所需，浏览器放大后只能复制或插值像素，细节会变软。服务端压缩会丢弃部分高频细节，高压缩率下文字和建筑边缘可能出现块状、振铃或涂抹。页面把较小图片放进大尺寸容器，或用高 DPI 屏幕显示时，也会放大上述缺陷。

系统会优先主图准确性，但官方页面也可能提供低分辨率图片。画廊会做尺寸和语义筛选，降低门槛补足数量时可能出现质量一般的图片。可以建议刷新、重新生成或优先查看清晰度较高的画廊图片；不要把所有模糊都归因于网络慢。

## 图片重复或与景区不匹配

系统会通过感知哈希去重，并使用视觉模型判断图片与景区名称、城市的语义匹配。去重和视觉检查不能保证百分之百正确。

不匹配可能来自同名景点、附近 POI、城市级通用图或公共图片元数据错误。应向用户说明图片来源和筛选策略，不应在没有证据时声称某张图百分百准确。

重复和错图是两个问题：哈希只能判断图片内容是否相同或近似，不能判断它是不是目标景区；语义模型能降低错配，但不能替代人工核验。若图片来自附近 POI 或同名景点，应优先从来源和实体关系解释，而不是简单说“缓存错了”。

## 页面显示 undefined 或空字段

`undefined` 通常表示前端拿到的结构与预期不一致，或某项异步数据尚未返回。应核对接口响应字段、缓存版本和页面状态。

单个字段缺失不应导致整页空白。票价、开放时间、天气等非关键字段允许为空，并使用“待确认”或“暂无数据”表达。

需要区分三种状态：字段尚未返回、字段明确为“暂无数据”、字段拿到了但不该展示为确定值。`undefined` 更接近前端取值或结构问题；`null`/空字符串可能是数据确实缺失；页面标注“待确认”则表示系统识别到证据不足。不要用一个固定原因解释所有空字段。

## 景区后台任务失败

后台任务可能因高德、官网、图片下载、视觉模型或超时失败。任务失败时应保留基础资料并明确说明哪一部分未完成。

如果错误可重试，可以提供重新加载建议；如果缺少配置，应指出配置类型但不能展示密钥内容。

任务失败不等于所有数据都不可用。应说明基础资料、官网核验、图片、摘要分别处于什么状态；若只是图片或天气失败，不要声称整页不可访问。重试前先判断是瞬时外部错误、配置缺失还是输入无效，避免无意义地重复执行。

## 交通方案加载失败

优先检查出发地是否填写、目的地是否有效、12306 查询是否返回、路线服务是否可用。

铁路无票或无直达不等同于系统故障。系统在可行时会继续分析中转或航班，但不会保证一定存在方案。

提示文案应体现差别：接口失败可说“当前暂时无法获取铁路结果，可以稍后重试”；业务无票可说“当前参考结果中没有可购买余票，建议查看其他时段或方式”；无直达可说“没有查到合适直达方案，正在/可以继续比较中转或航班”。不能把无票写成系统异常，也不能把查询失败写成“肯定没有票”。

## 如何表达排查结论

1. 有直接证据时给明确原因，例如“当前缺少地图安全密钥配置”。
2. 证据不足时给排序后的候选原因，说明下一步如何验证。
3. 用户可操作的动作放在前面，需要后端检查的动作放在后面。
4. 不展示内部异常、密钥、Cookie、完整堆栈或其他用户数据。
5. 复合故障先解决阻断整页显示的问题，再处理单个字段或图片质量问题。
